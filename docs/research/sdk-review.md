# SDK usability review

> **Status:** an opinion, 2026-11-13, after b12352 and the demo app. Nothing here is decided: items become decisions
> (`D<n>`) only when chosen. Findings are cited by ID.

The question: is the SDK, as an Android developer meets it, good enough to headline? This covers the interface, getting
a model and a backend, memory, and the rest. It ranks what stands out and what holds it back.

## Verdict

The depth is headline material, and rare. Few Android LLM SDKs offer all of llama-server in-process, a working Qualcomm
NPU path, conversation semantics equal to llama.cpp's own web UI, resumable Hugging Face downloads, and a fake for
tests. What stands between it and *irresistible* is the first ten minutes. Schemas are JSON strings. Getting a model
from Hugging Face is a separate module and a separate step. The memory check refuses models that would run. Each is
fixable without changing the architecture.

## The strongest points

1. **All of llama-server, in-process, with no socket.** 28 endpoints behind one C API (D12). Typed Kotlin covers chat,
   tools, structured output, thinking and slots; `rawRequest` reaches the rest. Upstream's features arrive with each pin
   bump, and the contract check proves they still match (F121).
2. **The NPU just works, and says why when it doesn't.** Add `llamabro-hexagon` and Hexagon is a device. The skeletons
   install themselves and are checked against their SHA-256 (F78). `DevicePolicy` (Auto, Prefer, Only) falls back
   device by device, and `LoadReport` names where the model and its encoder landed and why each attempt failed. The
   image encoder follows the model or goes where the app says (D53).
3. **Knowing before loading.** `estimateFit` projects memory per device without loading anything. `ContextSize.Auto`
   sizes the context to the phone. `devices()` and `backends()` describe the hardware. An app can tell a person "this
   model is too big for this phone" before a download, which most SDKs can't.
4. **`Conversation` does the hard parts.** It handles streaming events (prefill progress, reasoning, content, tool
   calls, results, timings) and runs the tool loop. It covers regenerate, `endReasoning`, `compact` when the context
   fills, `toJson` and restore, and a RAM prompt cache across chats. It matches llama.cpp's web UI by design, so it
   behaves the way upstream does.
5. **Lifecycle without traps.** `close()` returns at once and frees memory in the background. Loads after a close wait
   for the NPU's memory to come back (F124). One process-wide runtime, created cheaply on any thread.
6. **Downloads that survive real life.** `llamabro-hub` resolves a repo, picks a quantisation and a projector, and
   downloads with a resume (a 206 after a force-stop, F114-F116). Tokens come from the app's own
   store. The background worker is the demo's own (D64 adds one to the SDK).
7. **Testable apps.** `llamabro-testing`'s `FakeLlamaBro` scripts replies, timing and failures, so an app's tests need
   no model and no device (D27). The demo's 230-odd tests run on it.
8. **Speed is taken seriously, and every claim has a measurement.** MTP drafting and the delta-net patch (+66% NPU
   prefill with MTP) are both measured, and the ARM BF16 patch makes the CPU encoder 5.3x faster (F127). Each patch is
   kept only until upstream has an equivalent, with a written rule for when to drop it.

## What to improve, most valuable first

1. **Done (D57): the memory check is a warning the app can act on, not a refusal.** It refuses models that run, because
   it can't see the memory Android frees by closing cached apps, and it charges the whole prompt cache up front (F128).
   Today the demo gets around it with a fixed 4096 context. The SDK should offer this itself, for example a `memoryCheck
   = Warn` option that loads at the largest context that fits and reports the shortfall. Open since F128.
2. **Decided (D63): typed structured output.** `ResponseFormat` takes a JSON schema string. `generate<T>()` / `ask<T>()`
   would derive the schema from a `@Serializable` class and return a `T`, which llama-server's grammar guarantees will
   parse. This is the biggest headline gain for the least work. Decided 2026-11-15: `ask<T>` and `generate<T>` return a
   `Typed<T>`, in one `llamabro-typed` module with typed tools (D63, from F143). Not built yet.
3. **Decided (D61, D62): typed tools.** The loop exists. Declaring a tool still means writing its schema as a string and
   reading `args.string("city")`. A typed form, `tool<WeatherArgs>("get_weather", "…") { args -> … }`, removes both.
   Decided 2026-11-15: annotated toolboxes generated by KSP over a functional form, now in `llamabro-typed` (D61, D63),
   and the loop's handling of unknown tools, errors, threads and approval (D62), from F139-F142. Built 2026-11-15: the D62
   part (unknown tools, `LbToolError`, `LbToolAbort`, approval, `resume()` finishing a batch; the blocking-tool dispatch
   moves with the typed layer). Not built yet: the typed tools (D61).
4. **Decided (D64): one call from a Hugging Face name to a loaded model.** Today the hub downloads and the core loads,
   in two modules and two steps. A single call that downloads if needed, reports both progresses and loads, would make
   the five-minute example three lines: `llama.loadModel(Hub.model("Qwen/Qwen3.5-4B-GGUF"))`. Downloads already resume,
   so it stays safe. Decided 2026-11-15: `llama.loadModel(hub.model("…"))` through an open `ModelSource`, one
   `LoadProgress`, what is on the phone loads without the network, and background downloads in `llamabro-hub-work`
   (D64). Not built yet.
5. **Decided (D65): typed embeddings, rerank and speech.** They're reachable only through `rawRequest`. Typed calls
   would make private, offline search a headline of its own (already listed in [history.md](history.md#open-items)).
   Decided 2026-11-15: `embed` and `rerank` in core with typed errors, speech input (`Content.Audio`, `transcribe`), no
   speech output (D65). Not built yet.
6. **Decided (D66): native logs from the very start.** The log callback is installed after native init, so an init that
   fails or hangs says nothing in logcat. Route llama.cpp's log from the first call (found while debugging F129, which
   turned out not to be native). Decided 2026-11-15: the logger is attached before init, and logcat is the default when
   the app gives none (F144, D66). Built 2026-11-15 (283282f..7d2247b, and the review fixes after it). Only llama.cpp
   and ggml lines go through the log trampoline; llama-server's own lines (`SRV_*`, `SLT_*`, `COM_*`) still go to
   stdout and stderr, which Android discards (F22). Routing them is open.
7. **Decided (D67): cancelling a load.** Check that cancelling the `loadModel` coroutine aborts llama.cpp's load through
   the progress callback, rather than waiting for the load to finish. Decided 2026-11-15: a carried patch lets
   llama-server's load callback stop the weight reading (F145, D67). Not built yet.
8. **Decided (D68): search on the Hub, with each model's recommended settings.** Searching lives in the demo
   (`HfSearch.kt`), not in `llamabro-hub`, so every app writes its own: the query, grouping a model's many uploads,
   reading the file list, and the redirect and token handling. It also finds a model without its recommended sampling:
   GGUF uploads rarely carry `general.sampling.*` (F17), so a searched model runs on llama-server's generic values while
   the five catalog models get their cards' values (D60). A typed search in the hub module would group uploads, list
   sizes with fit, and read the recommended values where the Hub has them (the base model's `generation_config.json`,
   found through the `base_model` tag), returned as a `Sampling` the app can use as that model's default. Recorded
   2026-11-14 while designing the demo's sampling settings; the leading apps checked then (F136) apply recommended
   values only from their own curated lists. Decided 2026-11-15: search in `llamabro-hub` grouping only quantized
   re-uploads, sizes without a fit verdict, and recommended sampling only where the Hub has it, with its source (F146,
   D68). Not built yet.
9. **Decided (D69): revisit the demo's theme colours.** The demo carries PH's features to readers, so its palette (the
   light and dark tokens in `designsystem/theme/Tokens.kt`, demo design §8.6) is looked at again in PH, with the screens
   the new features add. Recorded 2026-11-14 at the user's request. The app's new icon (a llama on deep navy, purple to
   orange, supplied by the user 2026-11-15) replaces the placeholder pearl and is decided together with the palette.
   Decided 2026-11-15: a neutral near-white and AMOLED near-black palette with the ink as primary, the icon's warmth
   only in the orb, and the icon as an adaptive and themed launcher icon (D69). Not built yet.
10. **Breadth that a headline will be asked about.** No non-Qualcomm phone verified. GPU drafting aborts and Vulkan
    waits on upstream (F125). No CI, sanitizer runs or generated API docs. Publishing waits on a decision about the NPU
    runtime's licence. None of these is visible in a demo, but each comes up in the first issue a reader opens.
11. **Decided (D70): entry points a DI container can build.** `LlamaBro.getInstance(context)` and
    `LlamaBroHub.getInstance(context)` are process-wide singletons configured through the `Application`
    (`ConfigProvider`), read once, so a DI container cannot construct or configure them, and the hub's `cacheDir` can't
    change without a restart. A public factory (`LlamaBroHub(context, config)` and the like) with the singletons kept as
    a convenience would fix it; core's native runtime is process-wide, so its factory must still refuse a second,
    different config. Required, recorded 2026-11-15 at the user's request, to be designed later in PH. Decided
    2026-11-15: `LlamaBro.create` and `LlamaBroHub.create` (one per config, one hub per folder) replace the singletons,
    and `llamabro-testing` gains `FakeLlamaBroHub` (D70). The factories are built, 2026-11-15 (106e21f, 08dd0ad,
    04b5572); the fake comes in W5.

## Where the work goes

No planned phase covers these yet: the history ends with the work after PD, and only the bindings, CI and generated
API documentation are named for later. Proposed, for a decision:

| Phase | Covers | Why together |
|---|---|---|
| **PH: the headline API** | Items 2-9 and 11: typed structured output and tools, loading by a Hugging Face name, typed embeddings, rerank and speech, native logs from the first call, cancelling a load, search with recommended settings, a revisit of the demo's theme colours with its new icon, and entry points a DI container can build | All are additions to the public Kotlin API over what llama-server already does. Each is testable on the host with the fake engine, and the demo can show 2-4 at once |
| **PR: release** | Item 10: CI, sanitizer runs, generated API docs, a second phone (non-Qualcomm), the NPU runtime's licence and publishing | What a public release needs, and none of it changes the API |
| Later | Flutter and Kotlin Multiplatform bindings over the C API (planned since P1), Vulkan and GPU drafting when upstream lands them (F125) | Waits on PH's API settling, or on upstream |

## A headline that the SDK could carry after items 1-4

> On-device LLMs on Android in a few lines of Kotlin: load any Hugging Face GGUF by name and run it on the phone's NPU.
> Get typed objects and typed tool calls back, and the SDK tells you whether a model will fit before you download it.
