# llama.cpp patches

The SDK never edits the llama.cpp submodule. Every change to it is a patch here, applied in name order to a build copy
(`sdk/native/build/llama.cpp`) by `sdk/native/scripts/prepare-llama.sh`, which Gradle's `prepareLlama` task runs before
every native build. A patch that no longer applies stops the build. Each speed patch must have won an A/B on the phone
([D10](../../../docs/decisions.md)); a functional patch, such as `0003`, is checked by tests instead.

| Patch | Origin | Why | Evidence | Drop when |
|---|---|---|---|---|
| `0001-hexagon-gdn-long-batch.patch` | Ours; one line, the change to propose upstream ([upstream-notes.md](../../../research/ph/delta-net/upstream-notes.md)), nothing posted | NPU prefill with MTP: Hexagon's fast chunked delta-net kernel was gated on K = 1, so with MTP (K = 4) prompts fell to the slow recurrent kernel. The gate also accepts `n_tokens > K`, where ggml's contract only promises slot 0 (`ggml.h`), as CUDA's chunked kernel already does. +61% at b12352, as fast as the head/tail split it replaced, and drifts less than upstream's own MTP on/off; applies unchanged at b12479, where it gives +67% (F163) | F7, F8, F121, F149, F163, D80 | Upstream's gate accepts `n_tokens > K` (`htp-kparams.cpp`, `K == 1`), or GDN replay (PR #31669, +114% on the phone, F149) is on by default in the pin; re-measure at every upgrade |
| `0002-bf16-neon-vec-dot.patch` | Upstream PR [#30432](https://github.com/ggml-org/llama.cpp/pull/30432) (head `cde3115c`), unmerged at b12479 (2026-11-17) | ggml-cpu has no ARM path for BF16 dot products (issue [#29917](https://github.com/ggml-org/llama.cpp/issues/29917)); the CPU image encoder with a BF16 projector 16.5 s → 3.1 s | F123, F127 | #30432, or another ARM BF16 path, is in the pinned build |
| `0003-load-progress-stop-hook.patch` | Ours; written up as reference for upstream ([upstream-pr.md](../../../research/ph/load-cancel/upstream-pr.md)), nothing posted | A cancelled load can't stop reading weights: llama-server's load progress callback always says go on. The patch adds `server_context::set_load_abort_callback`, asked before the 200 ms throttle, for the text model, the draft and the image encoder ([D67](../../../docs/decisions.md)). Ported to b12479's server refactor without a change in behaviour: the same three load stages call the same callback (F163). Stages without a progress call (context creation, warm-up, kernel compile) can't be stopped, though with an mmproj or a draft a cancel during the text model's is caught at the next stage's first tick (`server-context.cpp` ~1315-1404 at b12479, patched). Functional, not speed: no A/B; checked by the `load_stops_*` native tests and the phone timing | F145, F163 | Upstream has an equivalent hook (or its progress callback lets an embedder stop the load) |
| `0004-hybrid-swa-checkpoint-restore.patch` | Ours; upstream issue and PR drafted (`research/ph/cache-stop/`), nothing posted | On the LFM3 family (hybrid with SWA layers, `sliding_window: 256`), llama-server reuses the live slot state or a checkpoint only if its `pos_min` is n_swa - 2 before the shared prefix's end, but there `pos_min` is the recurrent position, equal to the state's end. So neither the live state nor the checkpoint 4 tokens before the previous prompt's end is ever reused: each turn re-processes the whole last user message, its audio encoded again (F152), or the whole chat while messages are short. The patch applies the SWA threshold only to partly removable memory (the fix tested on upstream master). Since b12479 the threshold lives in `server_prompt::get_reuse` (`server-slot-sched.cpp`), unchanged, and the patch passes it the SWA window only when `seq_rm_type == PART`, else 0; otherwise the state must end before the first token to evaluate, upstream's rule without SWA. Models without SWA layers (LFM2, LFM2.5, Qwen3.5) and with partly removable memory (Llama, Gemma 3) are unchanged. Voice-note chat on the tiny model, turn 4: 811 → 1,206 of 1,237 tokens cached; LFM3-Omni-2B on the Mac CPU, 1,815 → 149 ms. Memory: without the patch fallbacks erased newer checkpoints; with it up to `--ctx-checkpoints` (8) survive per slot, at most 8 x a checkpoint's size more (about +11 MiB on LFM3-Omni-2B, 2.8 MiB each, also per RAM prompt cache entry; a saved slot grew 23.9 -> 36.0 MB), against +32.5 MiB for `--swa-full` (F153). The rule concerns all memory that cannot be partly removed, so DSV4-style compressed caches fall under it too (DSV4 reports n_swa 0, so it is unchanged today). Functional, not speed: no A/B; checked by the `hybrid_swa_cache_*` native tests (cache coverage, short chats and the live state, which fail without the patch; replies equal to an uncached run) and a phone measurement | F153, F163 | Upstream applies the SWA threshold only to partly removable memory (`server_prompt::get_reuse`, `pos_min_thold`) |
| `0005-lfm3a-depthformer-no-cpu-ops.patch` | Ours; upstream fact sheet to be written (`research/ph/speech-output/`), nothing posted | LFM3-Omni's depthformer (the part that samples each audio frame's codes) looked its codebook rows up through a flattened view of `a.gen.code.embd.weight`, the logits matmul's weight, and built its positions with `ggml_arange`. On Hexagon the first reads tiled bytes as rows (every `/tts` an empty WAV, F155) and the second is unsupported, so every pass hopped NPU → CPU → NPU. The patch reads each codebook's row from its own table (a 3-D `get_rows` on the weight itself, `inp_codes_cb`) and passes the positions in (`inp_pos_cb`). The graph then has no CPU op on the NPU: the depthformer 30.3 → 15.8 ms per frame. The same numbers on the CPU and Metal (byte-identical WAV). Applies unchanged at b12479, where `lfm3a-gen.cpp` is untouched and Hexagon still has no `ARANGE`. Functional and speed: checked by `omni_tts_same_audio_as_upstream` (native, the CPU audio unchanged) and `check.sh --device`'s `device-speech` (audio on the NPU, no unsupported op, at least 1.5× real time) | F155, F156 | Upstream's LFM3-Audio graph reads the per-codebook tables directly and takes positions as input (`tools/mtmd/models/lfm3a-gen.cpp`, `build_gen_code`), or Hexagon supports `ARANGE` and reads views of tiled weights |
| `0006-embd-only-output-skips-lm-head.patch` | Ours, shaped as upstream's own next step (`llama.h` calls the two output flags "for now equivalent"; `llama-batch.h` has "TODO: have dedicated output flags"); fact sheet to be written, nothing posted | Every `/tts` audio frame decoded the LM with its 2048 × 128,000 text head and sampled a text token that the audio step ignores (3.5-3.7 ms on the NPU, 0.7 ms of CPU per frame). The patch makes `llama_batch_ext_set_output_embd` and `llama_batch_ext_set_output_logits` differ: each entry keeps both flags, and a decode whose outputs all asked for embeddings only leaves the LM head out of the graph (`cparams.logits`, beside upstream's own skip for pooled embeddings in `build_logits`); `llama_get_logits_ith` then fails. Graph reserves keep the head (the worst case), backend samplers and `llama_batch` callers always get it, and so do the rows `output_all` turns on. LFM3's speech helper asks for embeddings only on a frame while speaking alone (pure audio, not continuing), and `/tts` samples no text token while the next step is audio, as upstream's realtime route already does (`sample_next`). Upstream's YuE2 NAR decode, the one other caller of `set_output_embd`, reads only embeddings and skips the head too. Replaces the b12352 version, which added `llama_set_logits` (staging header `llama-ext.h`) and had the server turn the head back on per batch. Speed, checked for unchanged output: `omni_tts_same_audio_as_upstream` (CPU WAV byte-identical); on the NPU 38.3 → 33.8 ms per frame, as the old version; `device-speech` 2.31 times real time | F156, F165, D94 | Upstream makes the two output flags differ (then only the helper's frame hunk and the server's sample skip remain), or skips the head for audio-only frames itself |
| `0007-hexagon-poll-noblock.patch` | Ours; upstream's own Windows branch made unconditional, fact sheet to be written, nothing posted | With polling on (`GGML_HEXAGON_OPPOLL=1`, `npuPolling`, D86), every empty poll was a zero-timeout `dspqueue_read`, which on Android has `libcdsprpc` log an error: tens of thousands of lines a second, and the phone's log quota then drops the app's own lines. `htp-drv.cpp` already used `dspqueue_read_noblock` for a zero timeout, but only `#ifdef _WIN32`; the patch does so wherever the symbol loaded. Speech on the NPU 2.26 → 2.27/2.26 times real time; error lines 2,900 → 0. Applies unchanged at b12479 (`htp-drv.cpp` still reads without blocking only `#ifdef _WIN32`). `npuPolling` stays off by default (D90); the patch is what makes turning it on safe on Android | F162 | Upstream polls with the no-block read on Android too (`htp-drv.cpp`, `dspqueue_read`) |
| `0008-lfm3-speech-tail-guard.patch` | Ours; measured on 600 realtime replies (`research/voice/`), nothing posted | In a captioned (text-and-audio) reply, LFM3-Omni speaks the rest of its text with audio alone after `<|text_end|>` and in about 1.6% of replies never samples the end-of-audio code: it loses its place and plays near-silence with noise bursts, or garbled speech, until the context is full. Upstream's loop matches Liquid's reference, which relies on the caller's token cap. The patch watches the speech after the text ends in LFM3's helper: 3 s of near-silence (80 ms frames under RMS 0.004) or more than 5 audio frames per text token plus 13 turns the next frame into the end-of-audio frame and ends the response. Stopped all 10 failures in 600 replies (400 to choose the thresholds, 200 fresh) and cut no clean reply; clean replies are byte-identical. Functional: checked by the sweep and its replay (`realtime-sweep.sh`, `tail-guard-sim.py`), by `omni_tts_same_audio_as_upstream` (TTS untouched) and by ear | F167, D96 | The model ends its speech reliably (a later LFM3 release), or upstream bounds audio after the text itself |

Dropped: `0005-hexagon-keep-shared-weights-flat.patch` (F155), which kept any weight read by an op other than a matmul
out of Hexagon's tiled layout. Patch 0005 above removes the only such read in the models we ship, and the keep-flat
version sent that matmul to the CPU. It is kept at `research/ph/speech-output/hexagon-keep-shared-weights-flat.patch`
for a model that needs it.

**At every llama.cpp upgrade** (the checklist in [CONTRIBUTING.md](../../../CONTRIBUTING.md#upgrading-llamacpp)), check
each row's "Drop when" first. For a patch from an upstream PR:
`gh pr view <number> --repo ggml-org/llama.cpp --json state,mergeCommit` and, if merged,
`git -C sdk/native/third_party/llama.cpp merge-base --is-ancestor <mergeCommit> HEAD`. If the fix is in the new pin,
delete the patch and its row, and record it in the upgrade's finding. If the PR changed before merging, use the merged
version, not the one carried here.
