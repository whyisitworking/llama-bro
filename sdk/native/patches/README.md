# llama.cpp patches

The SDK never edits the llama.cpp submodule. Every change to it is a patch here, applied in name order to a build copy
(`sdk/native/build/llama.cpp`) by `sdk/native/scripts/prepare-llama.sh`, which Gradle's `prepareLlama` task runs before
every native build. A patch that no longer applies stops the build. Each speed patch must have won an A/B on the phone
([D10](../../../docs/decisions.md)); a functional patch, such as `0003`, is checked by tests instead.

| Patch | Origin | Why | Evidence | Drop when |
|---|---|---|---|---|
| `0001-hexagon-gdn-long-batch.patch` | Ours; one line, the change to propose upstream ([upstream-notes.md](../../../research/ph/delta-net/upstream-notes.md)), nothing posted | NPU prefill with MTP: Hexagon's fast chunked delta-net kernel was gated on K = 1, so with MTP (K = 4) prompts fell to the slow recurrent kernel. The gate also accepts `n_tokens > K`, where ggml's contract only promises slot 0 (`ggml.h`), as CUDA's chunked kernel already does. +61% at b12352, as fast as the head/tail split it replaced, and drifts less than upstream's own MTP on/off | F7, F8, F121, F149, D80 | Upstream's gate accepts `n_tokens > K` (`htp-kparams.cpp`, `K == 1`), or GDN replay (PR #31669, +114% on the phone, F149) is on by default in the pin; re-measure at every upgrade |
| `0002-bf16-neon-vec-dot.patch` | Upstream PR [#30432](https://github.com/ggml-org/llama.cpp/pull/30432) (head `cde3115c`), unmerged at b12352 | ggml-cpu has no ARM path for BF16 dot products (issue [#29917](https://github.com/ggml-org/llama.cpp/issues/29917)); the CPU image encoder with a BF16 projector 16.5 s → 3.1 s | F123, F127 | #30432, or another ARM BF16 path, is in the pinned build |
| `0003-load-progress-stop-hook.patch` | Ours; written up as reference for upstream ([upstream-pr.md](../../../research/ph/load-cancel/upstream-pr.md)), nothing posted | A cancelled load can't stop reading weights: llama-server's load progress callback always says go on. The patch adds `server_context::set_load_abort_callback`, asked before the 200 ms throttle, for the text model, the draft and the image encoder ([D67](../../../docs/decisions.md)). Stages without a progress call (context creation, warm-up, kernel compile) can't be stopped, though with an mmproj or a draft a cancel during the text model's is caught at the next stage's first tick (`server-context.cpp` ~1306-1395). Functional, not speed: no A/B; checked by the `load_stops_*` native tests and the phone timing | F145 | Upstream has an equivalent hook (or its progress callback lets an embedder stop the load) |
| `0004-hybrid-swa-checkpoint-restore.patch` | Ours; upstream issue and PR drafted (`research/ph/cache-stop/`), nothing posted | On the LFM3 family (hybrid with SWA layers, `sliding_window: 256`), llama-server reuses the live slot state or a checkpoint only if its `pos_min` is n_swa - 2 before the shared prefix's end, but there `pos_min` is the recurrent position, equal to the state's end. So neither the live state nor the checkpoint 4 tokens before the previous prompt's end is ever reused: each turn re-processes the whole last user message, its audio encoded again (F152), or the whole chat while messages are short. The patch applies the SWA threshold only to partly removable memory (`use_swa = n_swa > 0 && seq_rm_type == PART`, the fix tested on upstream master); otherwise the state must end before the first token to evaluate, upstream's rule without SWA. Models without SWA layers (LFM2, LFM2.5, Qwen3.5) and with partly removable memory (Llama, Gemma 3) are unchanged. Voice-note chat on the tiny model, turn 4: 811 → 1,206 of 1,237 tokens cached; LFM3-Omni-2B on the Mac CPU, 1,815 → 149 ms. Memory: without the patch fallbacks erased newer checkpoints; with it up to `--ctx-checkpoints` (8) survive per slot, at most 8 x a checkpoint's size more (about +11 MiB on LFM3-Omni-2B, 2.8 MiB each, also per RAM prompt cache entry; a saved slot grew 23.9 -> 36.0 MB), against +32.5 MiB for `--swa-full` (F153). The rule concerns all memory that cannot be partly removed, so DSV4-style compressed caches fall under it too (DSV4 reports n_swa 0, so it is unchanged today). Functional, not speed: no A/B; checked by the `hybrid_swa_cache_*` native tests (cache coverage, short chats and the live state, which fail without the patch; replies equal to an uncached run) and a phone measurement | F153 | Upstream applies the SWA threshold only to partly removable memory (`server-context.cpp`, `pos_min_thold`; on master `server_prompt::get_reuse`) |
| `0005-hexagon-keep-shared-weights-flat.patch` | Ours; upstream fact sheet in `research/ph/speech-output/upstream-issue-hexagon.md`, nothing posted | Hexagon tiles each matmul's weight in place the first time it runs (runtime repacking, `ggml_hexagon_graph_repack`). A weight that another op also reads, here LFM3-Omni's depthformer codebook table (`a.gen.code.embd.weight`: the logits `MUL_MAT` and a `GET_ROWS` through a reshaped view), is then read as tiled bytes by that op, so with everything on the NPU every `/tts` request returns an empty WAV with no error. The language model's shared `token_embd` escapes only because upstream keeps it in a host buffer. The patch marks a weight that any op other than a matmul's weight slot reads, directly or through a view, as keep-flat on the tensor (a host-only flag bit), unpacks it if it was already tiled, and makes `can_tile` refuse it, so the matmul's kernel choice is flat too. A per-graph check is not enough: `ARANGE` runs on the CPU and splits the lookup and the matmul into different graphs. On the phone only `a.gen.code.embd.weight` stays flat; the text model is unchanged. Speech on the NPU: 1.33-1.39× real time, against 1.7× with the speech part on the CPU (F154), so the CPU split stays the recommendation. Functional, not speed: no A/B; checked by `check.sh --device`'s `device-speech` step (`tests/device-speech/run.sh`), which fails without the patch | F155 | Upstream keeps such weights flat, or Hexagon's `GET_ROWS` reads tiled weights (`ggml-hexagon.cpp`, `ggml_hexagon_graph_repack`) |

**At every llama.cpp upgrade** (the checklist in [CONTRIBUTING.md](../../../CONTRIBUTING.md#upgrading-llamacpp)), check
each row's "Drop when" first. For a patch from an upstream PR:
`gh pr view <number> --repo ggml-org/llama.cpp --json state,mergeCommit` and, if merged,
`git -C sdk/native/third_party/llama.cpp merge-base --is-ancestor <mergeCommit> HEAD`. If the fix is in the new pin,
delete the patch and its row, and record it in the upgrade's finding. If the PR changed before merging, use the merged
version, not the one carried here.
