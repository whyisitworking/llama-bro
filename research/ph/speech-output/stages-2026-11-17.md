# Where a speech frame's time goes, and what makes the NPU fast (2026-11-17)

LFM3-Omni-2B `/tts` on the phone, the 55-word text with seed 42 (19.8 s of audio, ~248 frames of 80 ms), one
llama-server per configuration, the phone cooled to thermal status 0 before each. Script: `tts-stages.sh`. Build: the
research diff `stages-research.patch` on top of patches 0001-0005, every change behind an environment switch:

| Switch | What it does |
|---|---|
| `LB_TTIME=1` | per-stage wall time (`LBTT` lines): the LM step, the depthformer (3 MaskGIT passes + the feedback pass, with the graph build, allocation, inputs and compute), the codec, the server's text sample; Hexagon's host-side preparation (`LBHEX`) |
| `LB_NO_HEAD=1` | an embeddings context skips the LM's text head (`llm_graph_context::build_logits`), and the server samples no text token while `next_is_text()` is false |
| `LB_GR3D=1` | the depthformer reads each codebook's row from its own table, a 3-D `GET_ROWS` on `a.gen.code.embd.weight` itself, not a flattened view (the graph fix of F155) |
| `LB_POS_INPUT=1` | the depthformer's positions are an input (0..11) instead of `ARANGE`, which Hexagon does not support |
| `LB_KEEP_FLAT=1` | patch 0005's keep-flat marking (otherwise off in this build) |
| `LB_HEX_CACHE=N` | Hexagon keeps the prepared ops of the last N graphs (upstream keeps one) |
| `GGML_HEXAGON_OPPOLL=1` | upstream's switch: the host thread polls for NPU completions instead of sleeping |
| `-fa on` | flash attention, also in the speech graph |

## Results (ms per frame)

| Configuration | Real time | LM step | Depthformer | Codec | Text sample | Graph alloc |
|---|---|---|---|---|---|---|
| Split (`--no-mmproj-offload`, F154) | 1.68× | 23.9 | 19.3 (CPU) | 3.1 | 0.67 | 0.28 |
| Split, no text head | 1.83× | 20.5 | 19.4 | 3.2 | — | 0.28 |
| Split, no head, polling | 1.79× | 20.6 | 20.3 | 3.2 | — | 0.25 |
| NPU, keep-flat | 1.32× | 25.0 | 30.8 | 3.5 | 0.66 | 0.86 |
| NPU, keep-flat, positions input | 1.40× | 24.8 | 27.6 | 3.5 | 0.66 | 0.84 |
| NPU, graph fix | 1.34× | 24.6 | 30.3 | 3.4 | 0.72 | 0.80 |
| NPU, graph fix, positions input | 1.53-1.55× | 26.2-26.5 | 15.5-15.8 | 6.6-6.7 | 2.6-2.7 | 2.8-3.0 |
| + polling | 2.04× | 24.2 | 10.6 | 3.2 | 0.66 | 0.72 |
| + no head (no polling) | 1.76× | 22.5 | 15.5 | 6.8 | — | 2.92 |
| + no head + polling | 2.31× | 20.4 | 10.6 | 3.2 | — | 0.69 |
| + no head + polling + `-fa on` | 2.36-2.38× | 20.2-20.3 | 9.9-10.0 | 3.1-3.2 | — | 0.69 |
| + the above + `LB_HEX_CACHE=8` | 2.36× | 20.4 | 10.0 | 3.1 | — | — |

- **The ARANGE hop is the big one.** With the graph fix and positions as an input, the speech graph has no CPU op left
  and the depthformer drops from 30.3 to 15.8 ms (faster than the CPU's 19.3). Keep-flat cannot get there: its
  codebook matmul still runs on the CPU, so the graph still splits.
- **The CPU's clock is the second.** With all work on the NPU the host thread mostly sleeps between submissions, and
  everything it still does runs 3-4× slower (text sample 0.7 → 2.6 ms, graph allocation 0.8 → 2.9 ms, the codec's
  host side 3.4 → 6.7 ms). Polling keeps the core busy and the clock up: 1.55× → 2.04×. Likely frequency scaling
  (not measured directly); the split keeps the CPU busy and gains nothing from polling.
- **The text head is waste.** Every audio frame computed the 2048 × 128,000 head (3.5-3.7 ms on the NPU) and sampled a
  text token the audio branch ignores. Skipping both: −3.4 ms LM, −0.7 ms sampling, bit-identical audio (Mac CPU and
  phone).
- Flash attention in the speech graph: −0.7 ms per frame (2.31 → 2.38×); it changes the arithmetic, so the audio is not
  bit-identical (19.92 s vs 19.84 s).
- Hexagon's host-side preparation is small (0.56 ms per frame in all, 0.24 ms for the LM graph); a multi-entry cache
  saves 0.12 ms. Not worth it.
- What is left at 2.37×, ~33.5 ms per frame: the LM step 20.3 ms (NPU compute for one token of a 2B model), the
  depthformer 10 ms (4 submissions), the codec 3.1 ms.

## Checks

- Mac CPU, seed 42: default, `LB_GR3D=1 LB_POS_INPUT=1` and `LB_NO_HEAD=1` give byte-identical WAVs to the
  unpatched build. Metal: the graph fix byte-identical too.
- Phone: the split with and without the head, and the NPU with and without polling and the head, are byte-identical
  in pairs. The NPU path differs from the split sample by sample (0.2% equal samples, same length), from the NPU's
  arithmetic.

## Power and heat over sustained speech (ADB over Wi-Fi, on battery)

`tts-sustained.sh` with `thermal-sampler.sh`: the 151-word text sentence by sentence, four times (32 requests, ~210 s
of audio), screen on, the phone on battery (ADB over Wi-Fi), one run per configuration. Power from `dumpsys battery`'s
battery current and voltage; that current refreshes every 10-25 s, so each run drops its first samples until the first
refresh (otherwise the idle value lingers into the run). The charge counter moves in 4 mAh steps and in delayed bursts,
so it is not used. Idle with the screen on: 97 mA at 4.40 V, 0.43 W.

| Configuration | Speed (first / last 4 requests) | Power | Above idle | Energy per audio second, above idle | Skin max | NPU max | CPU max | Thermal status |
|---|---|---|---|---|---|---|---|---|
| NPU, graph fix, positions input, no head, `-fa on`, polling | 2.31× (2.25 / 2.32) | 4.44 W | 4.01 W | 1.74 J | 56.3 °C | 89.6 °C | 67.2 °C | 0 |
| the same without polling | 1.77× (1.78 / 1.78) | 3.50 W | 3.07 W | 1.73 J | 52.5 °C | 79.1 °C | 57.9 °C | 0 |
| split (`--no-mmproj-offload`), no head | 1.72× (1.74 / 1.71) | 4.35 W | 3.92 W | 2.28 J | 55.0 °C | 83.0 °C | 73.7 °C | 1 |

- Polling draws about 0.9 W more and finishes about 30% sooner, so the energy per second of speech is the same; the
  phone runs hotter while it speaks (NPU 90 vs 79 °C, skin 56 vs 53 °C). Neither throttled over 90-118 s.
- The NPU path uses about 24% less energy per second of speech than the split.
- The `skin` sensor (HAL type 3) climbs with the chip (35 to 56 °C in 90 s), so it sits near the SoC, not on the
  back cover; read it as a relative measure.
- One run each, one phone: differences under ~10% are within noise.

## Why polling helps, and the alternatives (2026-11-17, ADB over Wi-Fi)

A third research build adds `LB_POLL_SLEEP_US=N` (check for the NPU's answer without blocking, sleep N µs between
empty checks) and counts the waits. Best NPU setup (graph fix, positions input, no head, `-fa on`), 55-word text:

| Waiting | Speed | Responses waited for | Empty checks | Time in `dspqueue_read` |
|---|---|---|---|---|
| blocking (default) | 1.75× | 1,499 (~6 per frame, one per graph) | 0 | 8.1 s |
| spin (`GGML_HEXAGON_OPPOLL=1`) | 2.34× | 1,499 | 8,380,969 | 7.2 s |
| check, sleep 50 µs | 1.87× | 1,499 | 57,856 | 0.28 s |
| check, sleep 200 µs | 1.85× | 1,499 | 27,313 | 0.17 s |
| check, sleep 1,000 µs | 1.80× | 1,499 | 7,867 | 0.10 s |

- It is not the wake-up delay: with 50 µs naps each of the ~6 waits per frame ends within ~0.1 ms, yet the speed stays
  near blocking. Nor the cluster clock (cores 0-5 averaged 2,396 vs 2,186 MHz with and without polling, sustained).
  What helps is the host core never going idle: any idle, even in 50 µs naps, leaves the following host work slow.
  Likely deep idle states (slow exit, and cold caches if the core powers down); not proven.
- So something must keep that core awake. Spinning does it at no extra energy per second of speech (see above). The
  other routes are operating-system hints only an app can use (Android's performance hints, ADPF), to be tried in the
  app during the voice-mode phase.
- Scheduling context: the shell-launched server runs in the root cgroups (all cores, no limits). An app runs in
  `top-app` while visible (usually boosted) and in `background` otherwise (often fewer cores). These numbers are for an
  unrestricted process; the SDK's own numbers, in the foreground and in the background, need the app.
