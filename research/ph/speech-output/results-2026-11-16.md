The 151-word runs are suspect both ways: without streaming the model never ended and ran to `n_predict` (1,200
frames, exactly 96 s); streaming, it ended at 34 s, short for ~60 s of text. LFM3 samples at temperature 0.4, so runs
differ; the clips need listening to before any quality claim. A first 11-word run gave 0.94× (4.0 s in 4.24 s). Speech output
streams (a chunk per 80 ms frame); a spoken chat reply exists only through `/v1/realtime`. The SDK's raw request
returns text and so corrupts audio (F74), so this ran outside the SDK.

The split (the language model on the NPU, the speech part, depthformer and codec in the mmproj, on the CPU) produces
speech 1.7 times faster than real time with the first audio in under 0.2 s, so the NPU's failure is in the speech part
alone. The maintainer listened to the CPU-only clips: clear. The 151-word split runs (26-27 s) are short for the text and
need listening to for skipped words.

## A fixed seed per sentence (2026-11-16, W9)

`tts-sentences.sh`: the 151-word text spoken a sentence per request (8 requests), voice `female`, split setup
(`-dev HTP0 -ngl 99 --no-mmproj-offload`), three passes: no seed (a new random seed per request, as before), seed 42
for every sentence, seed 7 for every sentence. Each pass is joined into one WAV with 0.3 s between sentences.

| Pass | Audio | Time | Speed |
|---|---|---|---|
| random seed | 52.1 s | 30.7 s | 1.70× |
| seed 42 | 53.9 s | 32.4 s | 1.66× |
| seed 7 | 53.4 s | 31.8 s | 1.68× |

The maintainer listened: the voice drifts between sentences in all three, so a fixed seed does not hold it. Not measured
further; a likely reason is that the seed fixes the sampling noise while each sentence is a different text, so the
sampled frames diverge from the first one anyway. Holding one voice across sentences probably needs the requests to
share state (one realtime session that keeps the previous sentence's audio in context), not a seed.

## Why the NPU gives empty audio, and a fix (2026-11-16, W9)

With everything on the NPU, `/tts` encodes the prompt, then stops at the first audio frame (`n_tokens = 0`) and returns
a 44-byte WAV with no error: LFM3's depthformer samples the end-of-audio code first. Bisected on the phone with
`GGML_HEXAGON_OPFILTER` (ops kept off the NPU) and Hexagon's switches:

| Setting (all on `-dev HTP0 -ngl 99`) | Short text |
|---|---|
| default | 44 bytes (empty) |
| `SOFT_MAX|SUM_ROWS|REPEAT|ADD|CONCAT` off the NPU | empty |
| `FLASH_ATTN_EXT|ROPE|SIGMOID`, `RMS_NORM|MUL|SWIGLU`, `CONT|SSM_CONV|GET_ROWS` off | empty |
| `MUL_MAT` off the NPU | 111 KB (speaks) |
| `GGML_HEXAGON_OPFUSION=0` / `GGML_HEXAGON_OPBATCH=1` | empty |
| `GGML_HEXAGON_RT_REPACK=0` (no runtime weight tiling) | 115 KB (speaks) |

`test-backend-ops` (a separate build with the depthformer's exact shapes: q8_0 2017×1024 in 12 batches, the q8_0
projections, the f32 attention products, permuted and broadcast) passes all 18 on the NPU, so each op is right alone.
The cause is runtime repacking: Hexagon tiles each matmul's weight in place the first time it runs
(`ggml_hexagon_graph_repack`). The depthformer's codebook table `a.gen.code.embd.weight` is both the logits
`MUL_MAT`'s weight and the source of a `GET_ROWS` (through a reshaped view) that embeds the sampled codes. Once
tiled, `GET_ROWS` reads the tiled bytes as rows, the frame's input is garbage, and the first codes sampled end the
audio. The language model has the same sharing (`token_embd`), but upstream keeps that one in a host buffer
(`HTP0-HOST`), which is never tiled; the mmproj's weights all sit in the device buffer. A per-graph check is not
enough: `ARANGE` is not supported on the NPU, so the `GET_ROWS` and the `MUL_MAT` land in different graph splits.

The fix (carried as `sdk/native/patches/0005-hexagon-keep-shared-weights-flat.patch`): before tiling, any weight read by an op other than
a matmul's weight slot, directly or through a view, is marked keep-flat on the tensor (a host-only flag bit); if it
was already tiled it is unpacked back; `can_tile` refuses marked weights, so the matmul's kernel choice (`kparams`,
which asks `will_tile`) sees a flat weight. Correction (2026-11-17, a profiled run): Hexagon has no flat kernel for
quantized weights, so the NPU refuses that matmul (992 of 994 `supports-op` answers) and it runs on the CPU, splitting
the depthformer's graph NPU → CPU → NPU on every pass; likely part of why the NPU path trails the split. A better fix
would teach the NPU's `GET_ROWS` to read the tiled table (and the view to carry its base's tiled mark). A first version that only skipped the repack crashed the DSP
(`dspqueue_read failed`): the kernel was still chosen for a tiled weight.

With the fix, everything on the NPU (device tools built with it, `tts-measure.sh` and `tts-sentences.sh`):

| Text | Audio | Total | First audio | Speed |
|---|---|---|---|---|
| 11 words | 3.8 s | 3.3 s | — | 1.16× |
| 11 words, stream | 4.0 s | 3.0 s | 0.14 s | 1.36× |
| 55 words | 18.7 s | 13.5 s | — | 1.38× |
| 55 words, stream | 18.6 s | 13.3 s | 0.13 s | 1.39× |
| 151 words | 32.6 s | 23.6 s | — | 1.38× |
| 151 words, stream | 36.6 s | 26.5 s | 0.19 s | 1.38× |
| 151 words, a sentence per request (random / seed 42) | 50.9 / 53.2 s | 38.1 / 40.0 s | — | 1.34 / 1.33× |

So the NPU now speaks, but the split (speech part on the CPU, 1.66-1.73×) stays faster: the small depthformer runs
faster on the CPU than on the NPU.
