# Chat media without base64: file:// and raw buffers against base64 (W9 step 3, D84), 2026-11-17

`media-ab.sh` on the phone: LFM3-Omni-2B Q4_K_M with its Q8_0 mmproj on the NPU through the C API (`lb-run`, polling
on as `LlamaBroConfig`'s default), a chat holding three voice notes (macOS `say`, 16 kHz mono WAV: 26.7, 23.4 and
22.9 s, 2.3 MB together) with short replies, then a text question; the same body six times, one generated token each.
The first request fills the prompt cache; the other five measure the media path plus 4 new tokens (1,021 cached).
Research build: `media-research.patch` on the bridge and llama-server (`LB_MEDIA=file`: a path attachment becomes
`file://<path>` with `--media-path /`; `LB_MEDIA=raw`: the bridge's buffer address, copied once by a research branch
in `handle_media`; unset: base64 data URLs, as today).

| Variant | Round 1 | Round 2 | Round 3 | Server prompt |
|---|---|---|---|---|
| base64 (today) | 200 ms (191-203) | 192 ms (181-205) | 198 ms (189-202) | 40 ms |
| `file://` (upstream, `--media-path`) | 94 ms (84-104) | 94 ms (87-110) | 93 ms (86-95) | 40-41 ms |
| raw buffer (research patch) | 85 ms (76-89) | 93 ms (76-94) | 80 ms (78-88) | 40 ms |

Median of the five warm requests (min-max). First requests (cold, encoding the three clips): 3.6-4.6 s for all three.

- `file://` saves ~100 ms per turn with three voice notes in the history, about half the turn, and needs no llama.cpp
  change: llama-server reads the file itself (`server-common.cpp` `handle_media`, `fs_validate_filename`).
- A raw-buffer patch saves at most ~10 ms more, within the rounds' spread.
- The remaining ~45 ms above the prompt is llama-server decoding every clip again each turn to match its prompt cache;
  neither variant touches it.
- The first raw run failed ("failed to decode buffer"): the bridge frees attachments right after writing them into the
  body (`atts.clear()`), so a buffer handed by address must live until the request ends.
